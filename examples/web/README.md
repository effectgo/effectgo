# Typed errors from Go to Effect TS v4

This example shows that a Go handler error becomes a tagged error on the TypeScript side,
and that a new Go error the TypeScript code does not handle makes `tsc` fail. The routes use
`rt/web` (see `../../rt`). `ts/api.gen.ts` is generated by `effectgo ts` from the Go code
(see [the framework design](../../docs/design/framework.md), "The generator"); do not edit it.

## Layout

| Path | What it is |
|---|---|
| `contacts.go`, `errors.go` | in-memory store; `ContactNotFound` and `ValidationError` with `StatusCode() int` |
| `server.go` | `rt/web` routes and middleware (request ID, access log, body limit); errors are encoded by the framework |
| `main.go` | listens on `PORT` (default 8080; `0` picks a free port and prints it) |
| `server_test.go` | status codes and bodies for every route and error |
| `ts/api.gen.ts` | generated by `effectgo ts`, against `effect@4.0.4`: the schemas, the error classes and the `Api` with the group `store` |
| `ts/client.ts` | calls both endpoints through the generated client and handles the typed errors with `catchTag` |
| `ts/exhaustive.ts` | `catchTags` over every error of `updateContact` (business, `DecodeError`, `BodyTooLarge`, `InternalError`); the result is annotated with the generated `TransportError` only |

## Run

Go service:

```sh
cd examples/web
PORT=8080 go run .        # prints "listening on ..."
go test ./... && go vet ./...
```

TypeScript client (in another shell, with the service running):

```sh
cd examples/web/ts
npm install
BASE_URL=http://127.0.0.1:8080 npx tsx client.ts
npx tsc --noEmit
```

Analysis with effectgo (from the repository root, after building the binary):

```sh
go build -o bin/effectgo ./cmd/effectgo
cd examples/web && ../../bin/effectgo ./...        # diagnostics and summary
cd examples/web && ../../bin/effectgo sig ./...    # Effect<A, E, R> per function
```

## Regenerate

`ts/api.gen.ts` is generated. After a change to the Go handlers or their error types,
regenerate it from this directory (the binary is built from the repository root):

```sh
cd examples/web
../../bin/effectgo ts -name contacts -o ts/api.gen.ts ./...
```

`examples/run.sh` checks that the committed file matches the generator, and fails when it does not.

## Migrating a Huma execution handler

[migration_test.go](migration_test.go) is a runnable migration example using
`rt/web` and the standard library, without a Huma dependency. Run it with:

```sh
GOMAXPROCS=2 go test -p=1 -run TestMigrationHTTPContract -count=1 .
```

The three migration boundaries are explicit:

- Optional cookie/header inputs use `*string`. Missing values are nil; an empty
  cookie is a present pointer to `""`. The current runtime treats an empty header
  as absent. Plain `string` fields remain required and missing values produce
  `DecodeError` (400 with the default encoder). Optional decoding does not grant
  authentication: the handler decides whether an actor or either cookie is valid
  and returns 401 if none is accepted. The example's actor header and literal
  cookie values stand in for an application's authentication result; never trust
  a public actor header or authenticate by mere credential presence in production.
- Huma's `struct { Body Envelope }` is a transport wrapper. Return the envelope
  itself from `rt/web`, with a `Data` field tagged `json:"data"`, to keep
  `{"data": ...}` at the top level. `rt/web` JSON-encodes the entire return value;
  it does not unwrap `Body`. Huma output header/cookie fields also do not become
  response headers automatically. Use `http.ResponseWriter` middleware for
  headers and `http.SetCookie` for response cookies, with the existing security
  attributes preserved; document these separately in the OpenAPI response.
- `WithErrorEncoder` owns status, body, and Content-Type. The example keeps
  200/401 as `application/json` and 500 as `application/problem+json`, redacts
  internal errors, and checks actual HTTP responses against manual OpenAPI
  response metadata. Keep the existing `operationId` (`get-api-auth-me` in this
  example) and make the 200 schema describe the direct envelope. Register one
  execution handler; keep Huma documentation-only metadata separate from execution.

`web.ExternalError[E]()` declares an error shape/status for analysis and generated
clients; it does not describe media types, response headers, cookies, or operation
IDs. The current route API cannot replace manual OpenAPI metadata. No new generic
metadata layer is needed for this migration. Effect TypeScript remains `4.0.4`;
optional cookies still use the browser cookie jar through `BrowserFetchHttpClient`.


## Negative experiment

Add a Go error with a constant status to `UpdateContact` (for example `ContactLocked`
with `StatusCode() int { return 423 }`), regenerate, and run `npx tsc --noEmit` in `ts/`.
`tsc` fails in `exhaustive.ts`, because the new error is not assignable to `TransportError`.
Handle it in `exhaustive.ts` and `tsc` passes again. Do this in a copy: the committed
example has no such error.

## Conclusion

- The chain works end to end. The Go service returns `404 {"_tag":"ContactNotFound",…}`
  and `400 {"_tag":"ValidationError",…}`. The Effect v4 client decodes them against
  the schema annotated with `httpApiStatus`, and `Effect.catchTag` receives the class
  instance (`instanceof` is true).
- A business error that is in an endpoint's error list and not handled is a compile
  error (`exhaustive.ts`). The proof covers the TypeScript side only: the list in
  `api.gen.ts` is written by hand. The Go-to-TypeScript link is the generator (M3).
- v4 adds transport and decoding errors to every endpoint's error channel
  (`HttpClientError | Schema.SchemaError`), so the handled result is not `never`
  and the generator must emit those as well.
- `effectgo sig` infers the error sets of the service functions
  (`Store.GetContact`: `ContactNotFound`; `Store.UpdateContact`:
  `ContactNotFound | ValidationError`). It does not infer a set for the HTTP handler
  closures in `NewHandler`, and it does not see the 400 that the GET route returns for
  a non-integer id, because that check is in the adapter, not in a function that returns
  an error.
